# Cost and business-impact model

The measured-metrics and per-scenario cost tables below (through "Sensitivity analysis") are generated by `scripts/cost_model.py` and were re-run to confirm they're still current as of this revision -- they reproduced byte-for-byte. Automation metrics are measured directly from saved predictions and ground truth (nothing assumed). Each row is a single architecture on a single evaluation split -- rows are never blended across splits, so a dev row and a final-test row for the same architecture are reported separately rather than averaged into one number (per the project's rule against combining differently-denominated populations). The cost tables that follow apply configurable business assumptions to those measured rates across three labeled scenarios; changing the scenario never changes the measured metrics above it. The "Reading this model," "Cost per use and time-to-deploy," and "Headline conclusion" sections below are hand-written interpretation on top of that generated data, not themselves regenerated by the script -- disclosed here rather than implied to be fully automated end-to-end.

**Safe automation rate** = fraction of ALL claims that were both auto-resolved (not sent to a human) AND correct -- this INCLUDES a correct REQUEST_INFORMATION as "safe," so read it as "handled without a human," not as "resolved to a final APPROVE/REJECT." For the narrower claim, use **terminal-decision correct rate** (APPROVE/REJECT only, as a fraction of all claims) alongside it. This is the single number closest to "how much of this process can this system actually be trusted to run unattended," and it is why 40% incorrect does not mean 40% needs human review (item 30) -- incorrect automated decisions, escalations, and information requests are three different outcomes with three different costs, kept separate below rather than collapsed into one 'wrong' bucket.

## Sensitivity analysis: does the candidate's cost advantage survive its diagnostic final-run safety numbers? (no new LLM calls)

The candidate's cost advantage above is computed from its **development/validation** rates. `docs/second_touch_disclosure.md` discloses a separate, unauthorized, partial (30/50) guarded-agent run against final-test cases with materially worse safety (50% accuracy, 17.6% FAR) than any authorized number for this design. This section asks the real enterprise question: **if the candidate's true unseen-data performance looks like that diagnostic run rather than its dev/validation numbers, does it remain the cheaper architecture?** Reconstructed from real data (`ui/frontend/public/data/cases.json`'s guarded-agent field for all 50 final-test cases -- 20 deterministic-path cases, shared code with the frozen design, verified to match its decision on all 20 at $0 cost; 30 with a genuine, real-tool-call agent execution trace) and real per-case cost from `results/run_log.jsonl`'s `RESOLVER_V2`/`RESOLVER_V2_REGEN` entries -- **no new LLM calls were made for this analysis.** This reconstruction is diagnostic, not an authorized evaluation: it has no freeze manifest and its provenance could not be established from committed scripts or logging.

| Architecture | N | Automated rate | Escalation rate | FAR among automated | FRR among automated | Safe automation rate |
|---|---|---|---|---|---|---|
| Official frozen selective resolver (Exp 32) — final test | 50 | 78.0% | 22.0% | 0/27 = 0.0% | 13/26 = 50.0% | 42.0% |
| Guarded-agent candidate (Exp 52) — dev | 70 | 65.7% | 34.3% | 0/35 = 0.0% | 5/29 = 17.2% | 45.7% |
| Guarded-agent candidate (Exp 52) — validation | 30 | 66.7% | 33.3% | 0/14 = 0.0% | 3/14 = 21.4% | 50.0% |
| Guarded-agent candidate — DIAGNOSTIC final-run (unauthorized, n=30/50) | 50 | 66.0% | 34.0% | 3/24 = 12.5% | 3/21 = 14.3% | 50.0% |

**Cost per 1,000 claims if the candidate's real-world rates matched this diagnostic run, base scenario ($35/hr reviewer, 6 min/review, $150/false approval):**

| Architecture | Total expected cost/1,000 |
|---|---|
| Official frozen selective resolver (Exp 32) — final test | **$19170.46** |
| Guarded-agent candidate (Exp 52) — dev | **$12915.56** |
| Guarded-agent candidate (Exp 52) — validation | **$13500.69** |
| Guarded-agent candidate — DIAGNOSTIC final-run (unauthorized, n=30/50) | **$20393.37** |

**Answer: the candidate's cost advantage does NOT survive once its diagnostic final-run safety numbers are used instead of its dev/validation numbers.** Once false approvals are priced at meaningful business cost, degraded unseen-data safety erases the modeled advantage quickly -- exactly the failure mode a real deployment risks if development/validation-tuned rates do not hold on genuinely new data. This is the central reason the frozen selective resolver remains the official architecture for this project: it is the only one with a properly frozen, one-shot result to check against, and that check came back at 0 observed false approvals.

## Reading this model

The frozen selective resolver is computationally cheapest (near-zero AI cost), but this table is what determines whether it is operationally cheapest -- item 35's requirement. Do not read a low AI-cost number alone as a cost conclusion; read the **Total expected cost/1,000** column. All dollar figures under 'Assumption' are labeled, configurable business assumptions, not measured quantities; only the automation-metrics table above is measured. **Correction:** an earlier version of this model omitted false-rejection and unnecessary-information-request costs from the total even though both were already defined as assumptions -- the total now includes both, priced the same way as the false-approval cost (measured error rate among automated decisions, scaled to the per-1,000 volume). This changed which architecture is cheaper under development/validation rates -- but the sensitivity analysis above shows that advantage does not survive the candidate's diagnostic final-run safety numbers. See the headline conclusion below for how this project resolves the two findings.

## Cost per use and time-to-deploy

Cost per use (measured, from `docs/master_comparison.md`) and time-to-deploy are both business
considerations, not just token cost. Time-to-deploy here is **this project's own actual build/debug
experience**, not an estimate for a hypothetical team -- it is the real elapsed effort (in named
experiments, a proxy for calendar time and iteration count) each architecture took to reach a safe,
working state.

| Architecture | Cost per claim (measured) | Time-to-deploy (this project's actual experience) |
|---|---|---|
| Deterministic rules only | $0 | Fast to build, but needed 3 hardening-verification rounds (Exp 2) to confirm it wasn't relying on a shortcut the real dataset wouldn't offer |
| RAG (frozen config) | ~$0.0005-0.001/claim | 6 experiments to tune (chunking, top-K, retriever, metadata filter -- Exp 5-10) before freezing |
| Fixed workflow | $0 | 1 experiment to build (Exp 18), but reached an unsafe FAR immediately -- "fast to build" was not "fast to ship safely" |
| Official frozen selective resolver | ~$0.0005/claim | Built on top of the above; Exp 30 itself was fast once its inputs (rules + RAG) existed, reflecting that most of the real time cost was in the layers underneath it |
| Guarded-agent candidate | ~$0.0013/claim (dev) | **By far the longest**: roughly 20 named experiments (Exp 34-52) and seven distinct live-found bugs before reaching a safe, full-dataset state on development/validation -- and, per the sensitivity analysis above, still not proven safe on genuinely unseen data |

## Headline conclusion

**The frozen selective resolver remains the official recommended architecture for this project.** Not
because it is necessarily the cheapest architecture in theory -- under development/validation-selected
rates, the corrected cost model finds the guarded-agent candidate cheaper in every modeled scenario -- but
because the frozen resolver is the only architecture with a properly frozen, documented evaluation
contract and an official result to show for it: **30/50 (60%), 0/37 observed false approvals**, on a
one-shot run against data no design had seen before.

**The guarded-agent candidate is retained as a promising but unvalidated candidate, not promoted.** Its
development/validation results and the corrected cost model suggest it could be economically better. But
`docs/second_touch_disclosure.md`'s diagnostic final-run data -- unauthorized and partial, but real --
showed materially worse safety (50% accuracy, 17.6% FAR) on unseen final-test cases, and the sensitivity
analysis above shows that once false approvals are priced at meaningful business cost, that degradation
erases the modeled cost advantage. That is sufficient reason not to promote it, even though it cannot
establish the candidate's true generalization performance (the final-test set is no longer a clean
holdout, and this run's provenance could not be established from committed scripts or logging).

**The cost conclusion is therefore conditional, not absolute:**

> Under development/validation-selected operating rates, the guarded candidate is cheaper in the modeled
> scenarios. However, a later diagnostic run on previously unseen final cases produced materially worse
> safety, showing that the economic advantage is not yet robust to generalization failure.

No new held-out set was created for the candidate this session. That remains a deliberate choice, not an
oversight: **the guarded candidate warrants future evaluation on a fresh, untouched holdout before
promotion** -- not a re-run of the current final-test set, which is no longer independent for either
design.
