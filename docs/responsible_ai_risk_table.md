# Responsible AI risk table

Every row states what was actually built and tested, not an aspirational control. "Residual risk" is
stated honestly even where a mitigation exists — a mitigation reducing a risk is not the same as
eliminating it, and this project's own standing rule is never to claim a mitigation not actually evidenced
by an experiment.

| Risk | Failure mode | Current mitigation | Residual risk | Human control |
|---|---|---|---|---|
| **False approval** | A claim that should be rejected/escalated is auto-approved, paying an ineligible claim. | Selective architecture routes the LLM-residual step only to cases the deterministic layer can't resolve; the official Exp 32 result observed 0/37 false approvals; the guarded-agent candidate observed 0/52 and 0/22 on dev/validation. | Observed 0% on the populations tested, not a guarantee for unseen distributions or higher volume — no formal proof of zero false-approval probability exists. | ESCALATE is a first-class outcome; any claim the system can't resolve with confidence routes to a human reviewer rather than being auto-approved. |
| **Unsupported rejection** | A legitimate claim is rejected without a real policy basis, or on a hallucinated citation. | Decisions require `policy_evidence`; Exp 33's failure taxonomy separately tracks over-rejection as its own error class. | Not eliminated — Exp 32's REJECT recall was 0.92, meaning some legitimate claims can still be misjudged; citation correctness against the actual retrieved corpus was not adversarially tested (see the misinformation/citation gap below). | A rejected claim's stated policy evidence is inspectable by a reviewer, and REQUEST_INFORMATION exists as a softer alternative the system can choose instead of an outright reject. |
| **Missing evidence** | The system decides confidently despite lacking a required fact. | `REQUEST_INFORMATION` is a first-class outcome with named missing fields; H1-H4 hybrid-facts extraction (Exp 12) computes what's actually resolvable from visible data before any LLM step runs. | Missing-field precision/recall was not comprehensively measured across the full dataset in this session; some cases could still under- or over-request. | A human reviewer sees exactly which fields were flagged missing and can supply them directly rather than trusting an inferred guess. |
| **Conflicting enterprise records** | Two records disagree (e.g. two approvals for one expense) and the system silently picks one. | Fixed in Exp 28→30: `validate_approval` now detects >1 disagreeing approval record and returns `CONFLICTING_RECORDS`, mapped to ESCALATE. | Fixed only for the one case class found (duplicate/conflicting approvals); conflicting records in other tables were not exhaustively tested for the same failure mode. | Conflicting-record cases route to ESCALATE, so a human resolves the disagreement rather than the system guessing. |
| **Prompt injection** | Claim text or retrieved policy text contains an instruction designed to manipulate the model's decision. | Adversarially tested (Exp 28): note-based injections were partially defended (2 of several rejected safely, one failed closed at the step cap). Prompt-level defense treats retrieved/user text as data, not instructions. | **Not solved.** Exp 28 found retrieval-text injection fully succeeded in one attack (planted fake "policy" text produced an unsafe APPROVE in one turn, zero tool calls, the explanation literally repeating the injected claim) despite the explicit instruction that retrieved text is data. A social-engineering "verbal approval" note also produced an unsafe APPROVE. This is disclosed as an open, unresolved risk, not claimed as mitigated. | All decisions are logged with full evidence trails, so an injected decision is auditable after the fact even though it was not prevented; ESCALATE-eligible ambiguous cases still provide a human checkpoint for anything that doesn't cleanly resolve. |
| **Retrieval poisoning** | Malicious or fabricated text planted in the retrieved policy corpus is treated as authoritative. | Same Exp 28 test as above; the corpus itself is a fixed, allowlisted, synthetic 22-document set (not an open or user-editable index), which limits realistic attack surface versus an open web-scale corpus. | Directly demonstrated to succeed once (see Prompt injection row) — retrieval poisoning is the same underlying failure mode as prompt injection here, since injected text arrives via the retrieval channel. Not mitigated beyond the corpus being closed and allowlisted. | Same as prompt injection: post-hoc auditability, and ESCALATE as a safety net for cases that don't cleanly resolve. |
| **Wrong tool called** | The agent calls a tool that doesn't apply to the claim's actual situation. | Guardrails: read-only tools, typed argument schemas, call deduplication (Exp 20, 28); Exp 42/43 found and fixed two tools (`check_hotel_compliance`, `check_project_budget`) firing on the wrong claim type. | Found and fixed only the specific instances live-tested; no exhaustive proof no other tool can mis-fire on an untested claim shape. | Every tool call and its observation is logged in the trace, inspectable by a reviewer. |
| **Tool firing outside its domain** | A tool returns a disposition for a claim type it was never designed to judge. | Exp 43's domain guards: `check_hotel_compliance` and `check_project_budget` now check the claim's own type (`expense_type`) before returning an answer, closing the exact failure that caused two mis-fires in Exp 42. | The domain-guard pattern is applied to the tools known to need it; a not-yet-discovered domain mismatch in an untested tool/claim combination cannot be ruled out. | Disposition-gate overrides are logged distinctly from the model's own reasoning, so a reviewer can see when and why a tool's answer was trusted. |
| **Unreliable extracted input feeding deterministic code** | A deterministic tool computes a confidently wrong answer because the model-extracted input it received was wrong (a hallucinated date, a placeholder string, a miscounted value). | Found and fixed repeatedly, not assumed away: placeholder-string normalization (Exp 49), date-based night-count computed in code instead of trusting a model-supplied count (Exp 50), cross-checking an enterprise tool instead of a hardened free-text field (Exp 50). | This is an open-ended class of bug, not a closed one — Exp 47-52 found seven distinct instances of it by actually running the system, and the pattern (code is only as safe as its inputs) implies more may exist in claim shapes not yet tested. Determinism alone is insufficient; deterministic components must also have reliable inputs and validated applicability boundaries. | Every tool argument and its source (model-supplied vs. tool-computed) is in the trace, so a reviewer can spot a suspicious extracted value. |
| **Looping / repeated tool calls** | The agent calls the same tool repeatedly without converging, burning cost and turns. | Call deduplication (identical calls served from cache, not counted against the step cap) and a hard step cap, both tested in Exp 20/28; step-cap-reached falls back to ESCALATE rather than guessing. | Step-cap hits still occurred in some experiments (e.g. 3/13 runs in Exp 20, 5/13 in Exp 34, 8/13 in Exp 36) — the agent can still reach the cap; the mitigation is that it fails safe (ESCALATE), not that looping never happens. | A step-cap ESCALATE is visibly distinguishable in the trace from an ordinary escalation, so a reviewer knows the system ran out of budget rather than reasoned its way to ESCALATE. |
| **Cost explosion** | An unbounded number of model/tool calls drives cost far above expectation. | `MAX_BUDGET_USD` cap enforced project-wide; step cap bounds worst-case cost per claim; every call is cached, so repeat runs cost $0. Measured cost per claim across every architecture tested is at most a few cents (see `docs/master_comparison.md`). | At current measured pricing and workload, cost was not a material architecture-selection constraint — but this was not stress-tested at production-scale concurrent volume or against a pricing regime change. | Cost is logged per claim and per run; a monthly/scenario cost projection is modeled explicitly in `docs/cost_and_business_impact.md`, with assumptions labeled for a human to adjust. |
| **Provider failure** | The LLM API is unavailable or returns an error mid-decision. | Exp 28 tested malformed/unknown-tool/timeout scenarios; all failed closed (4/4) rather than guessing. | Only synthetic failure injection was tested, not a real extended outage or partial-response corruption under production load. | A failed call routes to ESCALATE, giving a human the claim rather than a system guess. |
| **Data / privacy concerns** | Real employee or company data is exposed or used. | The entire dataset, policy corpus, and enterprise tables are synthetic; no real employee or company data is used anywhere in this project (explicit scope exclusion, `problem.md` §7). | None applicable to real data, since none is used; this control does not extend automatically to a real deployment, which would need its own data-handling review. | N/A — no real personal data exists in this system to control access to. |
| **Synthetic-data limitation** | Results measured on a synthetic benchmark may not transfer to real-world claim distributions, phrasing, or fraud patterns. | Dataset hardened across three rounds specifically to avoid trivial shortcuts (structured-field shortcuts removed, facts pushed into free text); leakage tests enforce ground truth isolation. | This is a controlled synthetic enterprise benchmark; results are not direct evidence of production-world performance. Generated cases may inherit generator-model biases, and real employee behavior and policy ambiguity may be more complex than the archetypes modeled here. | A human deploying this system in production would need a fresh, real-world validation pass before trusting these numbers to transfer. |

## Governance framework alignment
See `docs/README.md`'s "Governance & security alignment" section for the mapping of these findings to
OWASP Top 10 for LLM Applications (2026), Singapore's IMDA Model AI Governance Framework, and the EU AI
Act's human-oversight principles. All 10 OWASP LLM categories have real test evidence, remapped from the
original 2025-edition assessment to the current 2026 numbering
(`docs/owasp_llm_top10_2026.md`): LLM03 (Excessive Agency) is directly mitigated; LLM01 (Prompt
Injection) is explicitly disclosed as tested-but-not-solved per the Prompt injection and Retrieval
poisoning rows above; LLM05 (Data/Model Poisoning) is scoped as not applicable with a reasoned
architectural argument; LLM08 (Hidden Context Exposure, renamed/broadened from "System Prompt Leakage") is
disclosed as only partially tested under its new, wider 2026 scope; and LLM02, LLM04, LLM06, LLM07, LLM09,
LLM10 were each directly tested or scoped this pass, at $0 cost, with no new unmitigated vulnerability
found — though LLM02's clean result rests on a parse-failure-to-ESCALATE fallback rather than a
demonstrated deliberate model refusal, disclosed as such rather than overclaimed.
