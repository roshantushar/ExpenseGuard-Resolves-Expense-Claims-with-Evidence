# Synthetic-data provenance and limitations

## Provenance (item 45)

| Element | Detail |
|---|---|
| Generator | `dataset_generator/` — `build.py` (orchestrator), `world.py` (fixed world state), `cases_a.py`/`cases_b.py`/`cases_c.py` (the three architecture-group case generators: self-contained, fixed-workflow, dynamic-agent-candidate), `engine.py` (the hidden reference/ground-truth engine), `semantic.py` (the free-text hardening layer), `policy_text.py`/`render.py`/`write_docs.py` (policy corpus prose and PDF rendering). |
| Generation model | `openai/gpt-4o-mini` (`dataset_generator/semantic.py:MODEL`), used to draft each claim's employee free-text note from the hidden structured facts, and to draft policy-corpus prose (`dataset_generator/policy_text.py`, cached in `commentary_cache.json`). |
| Random seed | `6202` (`dataset_generator/world.py:SEED`), consumed deterministically by `dataset_generator/build.py`; rebuilding with `python -m dataset_generator.build` reproduces the same case set. |
| Policy-generation method | A fixed, hand-authored global/regional/temporal policy structure (`policy_text.py`) rendered to prose by the generation model, cached so re-runs don't redraft already-approved text (`commentary_cache.json`, `semantic_cache.json`). |
| Enterprise-table generation | Deterministic, seeded synthetic fixtures generated by `world.py` alongside the case generators — approvals, delegations, travel requests, project/budget status, and prior-expense history, all derived from the same fixed seed. |
| Ground-truth generation/verification | `engine.py` computes the expected decision from the hidden structured facts (never from the free-text note); `semantic.py` then independently re-extracts facts from the generated free-text note (blind to the hidden facts) and re-runs the reference engine on that extraction to check the note still supports the same label — a small number of cases needed manual review when this automatic check disagreed (`semantic.py:MANUAL_OK`, three documented cases with the reviewer's reasoning inline). |
| Hardening rounds | Three rounds, documented in `docs/exp02_rules_baseline.md`: round 1 moved computed facts and distractor noise into free text; round 2 added dictated/local-language notes and coarsened the visible bill category; round 3 added directory-style lookups the parser could no longer shortcut. Each round was verified to actually degrade shallow field-matching (Exp 2's regex baseline: 65/70 → 54/70 → 48/70 on dev) while the hidden reference engine's own labels stayed exact. |
| Split generation | 70 development / 30 validation / 50 final test, assigned deterministically from the same seeded build (`dataset_generator/build.py`), stratified across the three architecture groups (`A_SELF_CONTAINED`, `B_WORKFLOW`, `C_AGENT_DYNAMIC`) and case families. |
| Freeze process | `experiments/exp32_freeze_manifest_v2.yaml`, committed before the one-shot Exp 32 run, hashes the code, policy corpus, enterprise data, ground truth, and the runner script itself. Documented caveat in `docs/exp32_final_test.md`: a later, in-session dataset regeneration (adding RAG-necessity cases) changed the on-disk dataset, so that manifest's hashes no longer verify the *current* files — the Exp 32 result remains the valid record of what ran against the snapshot that existed at the time, not a live-reproducible claim against today's dataset. |
| No post-hoc label changes | Ground-truth labels were not modified after Exp 32's run or after Exp 33's error analysis; `tests/test_no_leakage.py` enforces that runtime code never reads `04_ground_truth_PRIVATE/` at all. |

## Limitations (item 46)

- **This is a controlled synthetic enterprise benchmark.** Every claim, policy document, and enterprise
  record is generated, not observed from a real company's expense-processing history.
- **Results are not direct evidence of production-world performance.** A 60% final-test accuracy or a 0%
  observed false-approval rate describes this system's behavior on this dataset only; neither figure should
  be read as a forecast for a real deployment's claim distribution, volume, or adversarial pressure.
- **Generated cases may inherit generator-model biases.** Both the free-text notes and the policy-corpus
  prose were drafted by `openai/gpt-4o-mini`; any systematic phrasing habits, omissions, or stylistic
  tells of that model could make cases easier or harder for models to parse in a way that would not hold
  for genuinely human-written expense notes.
- **Real employee behavior and policy ambiguity may be more complex.** The dataset's hardening rounds
  deliberately inject difficulty (distractor sentences, coarsened categories, non-English notes), but the
  space of real-world phrasing, error, and intentional ambiguity is far larger than what three hardening
  rounds can approximate.
- **The independent-extraction verification catches gross mismatches, not subtle ones.** `semantic.py`'s
  automatic check confirms a note supports its label when re-extracted and re-run through the reference
  engine; it does not guarantee every note is maximally natural or free of any residual tell that could
  make a case easier than an equivalent real one.
- **No fraud, intent, or character inference is modeled or claimed**, consistent with `problem.md`'s
  explicit scope exclusion — this dataset does not attempt to simulate deceptive intent, only ambiguous or
  incomplete evidence.

## Leakage prevention (item 47)

- **Decision-critical structured fields were moved into free text.** The hardening rounds above exist
  specifically so a case can't be solved by reading a structured field the way the pre-hardening dataset
  allowed — nights, attendee counts, exception references, and even the expense category itself are only
  recoverable from the note's prose in the hardened dataset.
- **Rules were rerun after hardening — this is the project's active leakage test, not a passive audit.**
  Before hardening, a field-matching rule engine could solve most of the dataset directly from structured
  fields — an answer-shortcut, functionally equivalent to a leaked answer, sitting in the visible input.
  Exp 2 measured what happened to that same rule engine's accuracy after stripping the shortcut across all
  three hardening rounds: **65/70 → 54/70 → 48/70 on dev** for the regex-parsing baseline — a real,
  measured, reported drop confirming the shortcut was actually removed, not just obscured. This is the
  concrete "before/after stripping leakage" result: before hardening, the easy dataset let 2c-style rules
  reach 70/70 dev; after, the same code reaches 48/70 — the difference is exactly the leakage that was
  found and removed.
- **Final-test labels were never available to the system.** `04_ground_truth_PRIVATE/ground_truth.jsonl`
  is a physically separate file from every model-visible input; `tests/test_no_leakage.py` statically
  enforces that no runtime module (`resolver`, `agent`, `agent_variants`, `workflow_v2`, `rules_v2`, etc.)
  imports or reads it, and ground truth is joined only by evaluator code after a run completes.
- **Hash/freeze process.** `experiments/exp32_freeze_manifest_v2.yaml` hashes the resolver code, the policy
  corpus, the enterprise data, the ground truth, and the runner script itself, committed before the one-shot
  Exp 32 run — so the exact inputs that produced the official 30/50 result are independently verifiable
  against that manifest (with the caveat in the provenance table above about a later, disclosed dataset
  regeneration).
- **No changes to final-test labels after observing Exp 32.** Ground truth was not edited after the Exp 32
  run or after Exp 33's error analysis. This is a distinct guarantee from the one in
  `docs/README.md`'s methodology note: the *labels* were never touched, but the *architectures* built
  afterward were still informed by knowledge of Exp 33's error categories, which is why the original
  final-test set can no longer be treated as an unseen blind test for those later architectures even though
  no individual label was changed.
