# Cost and business-impact model

Generated by `scripts/v2/cost_model.py`. Automation metrics below are measured directly from saved predictions and ground truth (nothing assumed). Each row is a single architecture on a single evaluation split -- rows are never blended across splits, so a dev row and a final-test row for the same architecture are reported separately rather than averaged into one number (per the project's rule against combining differently-denominated populations). The cost tables that follow apply configurable business assumptions to those measured rates across three labeled scenarios; changing the scenario never changes the measured metrics above it.

## Cost per use and time-to-deploy

Cost per use (measured, from `docs/v2/master_comparison.md`) and time-to-deploy are both business
considerations, not just token cost. Time-to-deploy here is **this project's own actual build/debug
experience**, not an estimate for a hypothetical team -- it is the real elapsed effort (in named
experiments, a proxy for calendar time and iteration count) each architecture took to reach a safe,
working state.

| Architecture | Cost per claim (measured) | Time-to-deploy (this project's actual experience) |
|---|---|---|
| Deterministic rules only | $0 | Fast to build, but needed 3 hardening-verification rounds (Exp 2) to confirm it wasn't relying on a shortcut the real dataset wouldn't offer |
| RAG (frozen config) | ~$0.0005-0.001/claim | 6 experiments to tune (chunking, top-K, retriever, metadata filter -- Exp 5-10) before freezing |
| Fixed workflow | $0 | 1 experiment to build (Exp 18), but reached an unsafe FAR immediately -- "fast to build" was not "fast to ship safely" |
| Official frozen selective resolver | ~$0.0005/claim | Built on top of the above; Exp 30 itself was fast once its inputs (rules + RAG) existed, reflecting that most of the real time cost was in the layers underneath it |
| Guarded-agent candidate | ~$0.0013/claim (dev) | **By far the longest**: roughly 20 named experiments (Exp 34-52) and seven distinct live-found bugs before reaching a safe, full-dataset state -- direct evidence that agentic designs cost meaningfully more in engineering time, not just inference tokens, before they can be trusted |

The guarded candidate's time-to-deploy is the strongest evidence in this project that "an agent is more
capable" and "an agent is cheaper to ship" are different claims -- its per-claim inference cost is
trivially small, but the actual cost of reaching a trustworthy version of it was by far the largest time
investment in the whole project, which the token-cost-only view in the table below would never surface on
its own.

**Safe automation rate** = fraction of ALL claims that were both auto-resolved (not sent to a human) AND correct. This is the single number closest to "how much of this process can this system actually be trusted to run unattended," and it is why 40% incorrect does not mean 40% needs human review (item 30) -- incorrect automated decisions, escalations, and information requests are three different outcomes with three different costs, kept separate below rather than collapsed into one 'wrong' bucket.

**Are escalated/abstained cases actually the difficult ones? Measured, not assumed.** The "Accuracy (escalated, pre-human-review)" column above answers this directly: for the frozen resolver, cases it chose to escalate would have been guessed *correctly* 81.8-100% of the time had it guessed anyway -- meaning its escalation trigger is conservative (it sends some cases to a human it could plausibly have resolved itself), a safety-over-automation trade-off, not evidence those cases are hard. The guarded-agent candidate's escalated cases tell the opposite story: only 50-60% pre-review accuracy -- meaning its escalation trigger is doing real work, catching cases where a guess would have failed roughly half the time. Abstention/escalation is therefore not simply "failures set aside": for the candidate, ESCALATE correctly identifies genuinely hard cases; for the frozen design, it is a wider, more cautious net that also catches some it could have resolved.

## Reading this model

The frozen selective resolver is computationally cheapest (near-zero AI cost), but this table is what determines whether it is operationally cheapest -- item 35's requirement. Do not read a low AI-cost number alone as a cost conclusion; read the **Total expected cost/1,000** column. All dollar figures under 'Assumption' are labeled, configurable business assumptions, not measured quantities; only the automation-metrics table above is measured. This model does not include false-rejection or unnecessary-information-request costs in the per-1,000 total yet (their rates were not separated from general inaccuracy in this pass) -- treat the totals above as a partial, conservative estimate (a floor, not a ceiling) until that breakdown is added.

## Headline conclusion

**The best-performing AI architecture was not the best operating architecture.** ExpenseGuard found that
safe automation must be evaluated jointly on accuracy, false approvals, escalation burden, and total
cost-to-serve — not on accuracy or FAR alone.

| Dimension | Official frozen selective resolver | Guarded-agent candidate |
|---|---|---|
| Accuracy | Lower (60.0% final test / 61.4% dev) | Higher (62.9% dev / 70.0% validation) |
| False approvals | 0 observed | 0 observed |
| Escalation / human review | Lower (18.6% dev / 22.0% final test) | ~1.5-1.8x higher (34.3% dev / 33.3% validation) |
| Risk-adjusted operating cost per 1,000 claims | Lower, at every scenario tested | Higher, at every scenario tested |

**The guarded agent improved decision accuracy while preserving the observed false-approval safety
constraint, but increased escalation enough that human-review cost outweighed those gains. The simpler
frozen selective resolver therefore remained the preferred operating architecture under all tested
low/base/high cost scenarios.**

### Held-out-set decision: closed, not required
Per items 62-66, a new frozen holdout for the guarded-agent candidate would only be justified if its
business case were strong enough to seriously consider promoting it to the official architecture. This
cost analysis says the opposite: more complexity, more human review, higher total operating cost, and no
clear business justification for replacing the frozen design. A fresh holdout would therefore be answering
a question that is not currently decision-relevant. **This decision is closed as "not required" unless a
later analysis (a different cost scenario, a fix that meaningfully lowers the candidate's escalation rate,
or new business assumptions) changes the architecture-selection conclusion above.** The existing record
stands as the project's stopping point: official architecture is the frozen selective resolver; official
blind result is Exp 32's 30/50 (60%), 0 observed false approvals; the guarded agent is documented as
technically interesting — higher accuracy, matching safety — but operationally rejected because its
escalation burden increases total cost.

**Read the near-zero totals for long context, naive RAG, and the policy oracle with real caution, not as a
win.** Their low cost here comes from near-zero escalation and zero *false-approval* cost in this cost

same disclosed limitation as above), and their raw accuracy was 30-36%, far below the frozen design's

cheap in any complete sense — it is simply not yet penalized by the components this model currently prices.
The policy oracle additionally requires ground truth to run at all and cannot be deployed. These rows exist
to show the full ladder, not to argue any of them beat the frozen design.

## Does the guarded agent's additional complexity earn its keep? (item 36)

**Not on this cost model, at every scenario scale tested.** The official frozen resolver's total expected
cost/1,000 claims is lower than the guarded-agent candidate's in all three scenarios (e.g. base scenario:
$4,364.71-$5,170.46 frozen vs. $7,834.03-$8,058.42 candidate) — not because the candidate is less safe (its
FAR is 0% on both splits it has been measured on, matching the frozen design) but because its **escalation
rate is roughly 1.5-1.8x higher** (34.3% dev / 33.3% validation vs. the frozen design's 18.6% dev / 22.0%
final test), and human-review cost dominates every scenario's total. The candidate's real, measured
advantages — a few points of accuracy, and a modestly better safe-automation rate on dev (45.7% vs. 42.9%)
— do not currently outweigh the added human-review load in this cost model.

This directly answers item 37's question about Exp 52's 44/70 vs. Exp 30's 43/70: **the one-point dev
accuracy gain is not the real story.** The candidate's actual measured advantage is a slightly better safe
automation rate at matching FAR, achieved by escalating more often rather than by resolving more cases
correctly on its own — a real but modest difference, not a "major overall accuracy improvement" and, on
this cost model, not yet a net operational win. Any statement elsewhere in this project's docs that the
guarded-agent candidate "beats" the frozen design should be read as **accuracy- and FAR-scoped only**,
not as an operational-cost conclusion — this cost model is the more complete picture, and it currently
favors the frozen design.
